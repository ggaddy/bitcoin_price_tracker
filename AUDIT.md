**Current behavior and strengths**

- Three routes: dashboard, price retrieval, and presence updates. Visible tabs send presence and request prices every five seconds; presence expires after 15 seconds without an update.
- Price requests drive refreshes. The first viewer marks a full refresh pending; subsequent successful updates rotate through providers. Snapshots younger than ten seconds suppress refreshes, including a pending full refresh.
- Only the latest merged snapshot is retained. The recent commits deliberately introduced this behavior; the plan below preserves it.
- SQLite writes use a transaction, parameterized values, and foreign-key cascading. Database operations run through `spawn_blocking`, avoiding synchronous SQLite work on Tokio's async worker threads.
- The HTTP client is reused. Upstream URLs are fixed HTTPS endpoints. Session identifiers have character and length validation. The frontend has no third-party runtime assets.
- Seven ordinary tests cover presence helpers, source ordering, and snapshot replacement/pruning. One browser smoke test is ignored by default. There is no checked-in CI workflow.

**Findings, ordered by priority**

| Priority | Finding and evidence | Impact and proposed correction |
| --- | --- | --- |
| High | Upstream requests have no configured deadline, and the refresh mutex is held across network requests. See `src/main.rs:28`, `src/handlers.rs:55`, and `src/pricing.rs:56`. | A stalled provider can hold the refresh path indefinitely and make active-viewer requests queue instead of returning cached prices. Add connect/total timeouts and allow concurrent readers to receive the stored snapshot while a refresh is already running. Reqwest 0.12.28 documents [no total timeout by default](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html#method.timeout). |
| High | Provider failure prevents rotation from advancing: `refreshed_source` is persisted only after a successful fetch. Full refresh uses `try_join!`, while `full_refresh_pending` is cleared before success. See `src/pricing.rs:170`, `src/pricing.rs:218`, and `src/handlers.rs:69`. | A failing provider can starve healthy providers. One failure during initial refresh discards the other results; subsequent requests may repeatedly retry CoinGecko. The ten-second gate uses the last successful snapshot, so failures can trigger another upstream attempt on every queued request. Track attempts separately from successful data, advance rotation after attempted work, retain partial successes, and apply bounded backoff, including rate-limit responses. |
| High | Source prices have no individual timestamps; updating one source assigns a new timestamp to the whole merged snapshot. See `src/models.rs:4`, `src/pricing.rs:194`, and `src/pricing.rs:229`. | Old quotes can be displayed as LIVE and included in the average. Even normal rotation updates each source only about once per 40 seconds, plus scheduling/network delay. After a long idle period and failed full refresh, some quotes can be much older. Store last-success time and health per source; define a freshness policy separately from the ten-second request cadence. |
| High | Snapshot metadata and source rows are loaded in separate queries without a read transaction. Writers delete and replace the old snapshot. See `src/storage.rs:104` and `src/storage.rs:162`. | A writer can commit between the queries, leaving the reader with an old average and no matching source rows. See `src/ui.html:171`, `src/ui.html:246`, and `src/ui.html:261`. | Slow requests accumulate and responses can overwrite newer or paused UI state. Keep heartbeats independent if price retrieval can exceed the viewer TTL. |
| Medium | Session initialization assumes `crypto.randomUUID()` and session storage are available. Label or standardize quote types, explicitly select BTC/USD, reject invalid prices, and test provider error payloads. Preserve `f64` unless the application later needs accounting-grade arithmetic; changing numeric types alone does not solve these issues. |

Additional improvements:

- **Presence accuracy and resource limits:** the viewer count is captured before waiting for the refresh mutex (`src/handlers.rs:44`). Recheck it before starting upstream work so queued requests do not refresh after viewers leave. Presence is client-reported, and the map has no total entry cap; add bounded storage and request limits for public hosting. Use monotonic time for in-process TTLs/cooldowns. Signed `saturating_sub` does not clamp future snapshot timestamps to zero (`src/presence.rs:41`).
- **Browser presentation and accessibility:** display per-source age and degraded health; retain the last visible price on transient errors; replace variable `innerHTML` interpolation with DOM text nodes (`src/ui.html:224`, `src/ui.html:242`). Current upstream source names are fixed, so this is preventive hardening rather than a demonstrated remote injection vulnerability. Respect reduced-motion preferences and pause the Matrix animation while hidden (`src/ui.html:347`). Replace user-facing database terminology with price-update information.
- **Operations:** the runtime image defaults to root; there is no health route, graceful shutdown, or configurable bind address. Add a non-root user with a writable data volume, useful refresh/error logging, and a local health check that does not call providers. Document that process-local viewers and locking support a single application instance.
- **Build and test maintenance:** use `--locked` in image builds, declare the supported Rust toolchain, and automate formatting, Clippy, tests, and image checks. The Selenium runner uses a floating image tag, requires host Cargo, relies on host networking, and removes any existing container with its configured name. Use an isolated name, guaranteed cleanup, and documented engine/platform assumptions. Its ten-second seeded-price freshness window also makes the test vulnerable to slow browser startup and live upstream access.

**Implementation contract and proposed defaults**

These are planning decisions to implement and test, not descriptions of existing behavior. If implementation evidence calls for a different choice, record the reason in the change log.

| Area | Planned behavior |
| --- | --- |
| Application shape | Keep a single Rust service, SQLite, the embedded dashboard, and latest-only quote retention. Keep refreshes request-driven. Use a nonblocking attempt to acquire refresh ownership: the request that acquires it may perform bounded upstream work, while other requests serve the stored snapshot immediately. No background refresh loop is required. |
| Refresh cadence | Keep the ten-second minimum after a successful snapshot. Also enforce at least ten seconds between refresh attempt starts, including failures. Both gates must permit work. Use monotonic time for process-local cooldowns and viewer expiry; use Unix timestamps for persisted observations and display. |
| Network limits | Start with a two-second connect timeout and five-second total timeout per provider. A full refresh runs eligible providers concurrently and retains individual results. Browser price requests get an eight-second deadline; these values are explicit defaults subject to verification. |
| Provider retries | Track next provider, last attempt, consecutive failures, and next eligible time independently of the last successful quote. Advance rotation after an attempt. Use per-provider exponential delays of 10, 20, 40, 80, 160, then 300 seconds; reset on success. Honor a valid `Retry-After` when it requires a longer wait, without sleeping inside the request handler. If all providers are cooling down, serve stored data. |
| First viewer | Mark a full refresh requested on the transition from zero to one active viewer. Preserve that request while the global gates prevent work. A batch attempts every currently eligible provider; failed or cooling-down providers remain eligible for later recovery through their individual retry state. A new viewer activation during a batch must not be erased when that batch finishes. |
| Presence | Keep the five-second heartbeat and 15-second expiry. Recheck active viewers immediately before dispatching upstream work. Work already dispatched may complete and persist its result after the last viewer leaves. Never hold the viewer-map lock across network or database I/O. |
| Freshness | Start with a separate 90-second maximum source age, allowing ordinary four-source rotation plus request/polling delay. Unknown or future observation timestamps are not fresh. Freshness is recomputed on every response; a new snapshot timestamp does not refresh an unchanged source. |
| Aggregate and status | Average/spread use only finite, positive quotes within the freshness window. One qualifying source is enough for an indicative average; return coverage counts. `LIVE` requires all four sources fresh with no outstanding provider failure; partial coverage or a recent provider error is `DEGRADED`; retained quotes with none fresh are `STALE`; no usable quote is `UNAVAILABLE`. Keep the last known quotes visible with their ages. |
| HTTP compatibility | Preserve existing JSON field names during migration. Keep HTTP 200 when a stored quote exists, including a stale quote; use 503 when no usable quote has ever been stored, and 500 for a database read failure. Keep freshness-based `average_price`/`spread` nullable when no quote qualifies. Add an explicit status and coverage fields; document `stale` as true whenever the response is not fully LIVE. |
| Deployment | Support one application process per database. Keep runtime limits process-local and document their reset on restart. Initialize the success-age gate from persisted data so a restart does not immediately refetch a fresh snapshot. |
